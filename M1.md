# M1 — Nền tảng gRPC và cân bằng tải

## Mục tiêu

Xây dựng hệ thống Python dùng `grpc.aio` gồm một client và nhiều replica. Client tạo một channel cho mỗi backend trong `configs/backends.json` và chọn replica theo Round Robin hoặc Least Request. Cấu hình M1 dùng ba replica; hai thuật toán được chạy với cùng workload để so sánh latency, throughput và tỷ lệ lỗi.

## Phân công

### Lầu — Proto và backend gRPC

**File phụ trách:**

- `pyproject.toml`
- `api/workload.proto`
- `src/grpc_lb/generated/`
- `src/grpc_lb/server.py`
- `deploy/Dockerfile`
- `tests/test_server.py`

**Công việc:**

1. Khởi tạo dự án Python, khai báo dependency và lệnh sinh mã từ proto.
2. Định nghĩa unary RPC `Execute`; request có `run_id`, `request_id`, response có `backend_id`.
3. Cài server `grpc.aio` với thời gian xử lý và giới hạn tác vụ đồng thời cấu hình được.
4. Đo riêng thời gian chờ và thời gian thực thi tại replica.
5. Ghi một dòng JSONL cho mỗi request phía server với các trường `run_id`, `request_id`, `backend_id`, `queue_ms`, `service_ms`, `status`.
6. Xử lý deadline và request bị hủy để không giữ suất xử lý.
7. Cung cấp health service và trạng thái `SERVING`/`NOT_SERVING`.
8. Viết Dockerfile và kiểm thử server, gồm kiểm tra nội dung log.

`queue_ms` tính từ lúc handler nhận request đến lúc được cấp suất xử lý. `service_ms` tính từ lúc bắt đầu xử lý đến khi hoàn tất hoặc bị hủy. `status` dùng `ok`, `cancelled` hoặc `error`.

## Hai giao diện đã chốt

### RPC

Định nghĩa chính thức nằm trong [`api/workload.proto`](api/workload.proto):

```proto
service WorkloadService {
  rpc Execute(ExecuteRequest) returns (ExecuteResponse);
}

message ExecuteRequest {
  string run_id = 1;
  string request_id = 2;
}

message ExecuteResponse {
  string backend_id = 1;
}
```

Lầu sở hữu proto và mã sinh; Khoa chỉ gọi qua stub được sinh ra. Thời gian xử lý và giới hạn đồng thời là cấu hình của replica, không truyền trong từng request. Lỗi được trả bằng gRPC status code.

### Kết quả từ client

Định nghĩa chính thức nằm trong [`src/grpc_lb/contracts.py`](src/grpc_lb/contracts.py):

```python
async def execute(
    run_id: str,
    request_id: str,
    timeout_s: float,
) -> CallResult:
    ...
```

`CallResult` có các trường ổn định:

| Trường | Ý nghĩa |
|---|---|
| `run_id`, `request_id` | Liên kết dữ liệu của một request |
| `policy` | Policy đang chạy, ví dụ `round_robin`, `least_request` |
| `backend_id` | Backend đã chọn; `None` nếu không chọn được |
| `started_at_unix_ns` | Thời điểm bắt đầu theo Unix nanosecond |
| `latency_ms` | Latency đầu cuối, tính cả bước chọn backend |
| `status` | `ok`, `timeout`, `error` hoặc `no_backend` |
| `grpc_code` | Tên gRPC status code khi có lỗi |
| `error_message` | Chi tiết lỗi để chẩn đoán |
| `schema_version` | Phiên bản schema, hiện là `1` |

Khoa luôn trả `CallResult` cho thành công và lỗi thông thường. `asyncio.CancelledError` dùng để dừng chương trình phải được phát lại. Đạt chuyển `CallResult` thành một dòng JSONL mà không tự suy đoán lại trạng thái.

## Thứ tự tích hợp

1. Lầu và Khoa chạy một RPC từ client tới một replica, sau đó chạy hai policy với ba replica.
2. Đạt ghép bộ tạo tải và Docker Compose.
3. Đạt chạy thí nghiệm; Lầu và Khoa xử lý lỗi thuộc phần mình.

## Điều kiện hoàn thành M1

- [x] Client tạo và tái sử dụng một channel cho mỗi backend trong cấu hình; cấu hình M1 chạy với ba replica.
- [x] Round Robin và Least Request chạy trên cùng đường gọi RPC.
- [x] Bộ đếm Least Request trở về 0 sau khi toàn bộ RPC kết thúc.
- [x] Health checking loại backend `NOT_SERVING` và nhận lại khi `SERVING` trong kiểm thử.
- [ ] Replica dừng được loại và được nhận lại khi phục hồi.
- [x] Log client và server liên kết được bằng `run_id`, `request_id`, `backend_id`; log server có `queue_ms`, `service_ms` và `status`.
- [ ] Có kết quả cho replica tương đương, một replica chậm và dừng/phục hồi.
- [ ] Có dữ liệu gốc, p50/p95/p99, throughput và tỷ lệ lỗi/timeout.
- [ ] Người khác có thể chạy lại hệ thống và thí nghiệm từ hướng dẫn trong repo.

Đã kiểm tra: sau khi sửa mã sinh proto trên nhánh `Khoa`, 43 test client/server/metrics qua; thử ba server thật bằng Python với hai policy có 720/720 RPC thành công và log hai phía khớp. Các mục chưa đánh dấu dành cho nghiệm thu đầy đủ: dừng/khởi động lại tiến trình server, dữ liệu thí nghiệm được kiểm tra cách tính và hướng dẫn chạy tái lập. Đo lường và đóng gói Docker hoàn thiện ở bước cuối.
